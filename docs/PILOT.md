# הפעלת פיילוט SpeakReady

## פריסה ראשונה

ה־Compose מריץ MySQL, שרת API אחד, View ו־Caddy שמספק HTTPS וחיבורי WebSocket ל־Blazor.
רק Caddy חשוף החוצה; MySQL וה־API נמצאים ברשת הפנימית של Docker.

1. הכינו שרת Docker עם Compose, דומיין שמצביע אליו ופורטים 80/443 פתוחים.
2. העתיקו `.env.example` ל־`.env`, החליפו שתי סיסמאות MySQL בסיסמאות שונות וחזקות והגדירו דומיין ומפתח OpenAI.
   בחרו סיסמאות ללא `;` כדי לא לשבור את מחרוזת החיבור. הקובץ מוחרג מ־Git.
3. הריצו `docker compose up --build -d`. Caddy מנפיק תעודת HTTPS באופן אוטומטי.
4. צרו חשבון תלמיד, השלימו הקלטה ובדקו שהתקבל משוב. ודאו שרענון אינו מנתק את המשתמש.
5. בצעו בדיקת מיקרופון אמיתי ב־Chrome למחשב וב־Safari ב־iPhone לפני הזמנת תלמידים.

אין הגדרת domain/API key אוטומטית. בחירת מודלים תלויה בזמינות בחשבון OpenAI של המפעיל.
אם האתר עולה לפני שה־API מוכן, נסו שוב לאחר שהלוג מציג `Database and pilot content ready`.

## נתונים ושדרוג

- סכמת שבע הטבלאות המקוריות נשמרת. נוספו AuthSessions, AnalysisJobs, AnalysisUsage ו־PilotContent.
- האתחול משתמש ב־CREATE TABLE IF NOT EXISTS ואינו מוחק משתמשים או טבלאות קיימות.
- שלושת תרגילי הפיילוט נוצרים פעם אחת בעסקה תחת נעילה; הפעלה נוספת לא מכפילה או משנה אותם.
- חשבון תוכן פנימי מושבת נוצר כמחבר התרגילים ואינו יכול להתחבר.
- יש לגבות לפני שדרוג. מערכת האתחול אינה מנגנון migrations כללי; שינוי עתידי בעמודות קיימות ידרוש migration מפורש.
- גרסת ההתחברות החדשה מחזירה `{user, token, expiresAt}` במקום User בלבד. לקוחות ישנים של API.http דורשים עדכון.
- הפעלת שלבים 10–11 מיושמת כרישום אירועי אתחול/עיבוד ו־DataAnnotations משותפים; אין הדפסה של שאילתות או מידע אישי.

## תור עבודה ותקלות

הניסיון וקביעת המכסה נשמרים יחד בעסקה. מזהה שליחה חוזר מחזיר את אותו ניסיון.
ניתוח נעשה על ידי עובד רקע, עם timeout של שלוש דקות ו־lease של חמש דקות.
אם שרת נעצר באמצע ניתוח, העבודה תחזור לטיפול לאחר תפוגת ה־lease. אין צורך להעלות שוב.
התאוששות עשויה לחזור על קריאת ספק שבוצעה לפני הקריסה; מכסת המשתמש אינה מחויבת שוב,
אך ייתכן חיוב נוסף מצד הספק. מיועד לפיילוט קטן עם מופע API אחד.

כשל ספק מסומן Failed; התלמיד יכול לנסות שוב פעמיים, וכל ניסיון חוזר נכלל במכסה היומית.
שקט או תמלול שאינו ניתן להבנה מחייבים הקלטה חדשה. המשוב נשמר ואינו מחושב מחדש בפתיחת דוח.
אם ספק ה־AI מחזיר ציטוט שלא נמצא בתמלול, המשוב נפסל במקום להציג אותו כתשובת התלמיד.

מחיקת ניסיון מסירה את הרשומה והקובץ. אם השרת קרס בין פעולות קובץ ו־DB, בדקו קבצים יתומים
בתיקיית השמע מול `PracticeAttempts.AudioPath` והסירו רק קבצים שאינם משויכים ואינם העלאה פעילה.
מחיקה אינה מבטלת בקשת ספק שכבר יצאה. לאחר שחזור גיבוי יש לכבד מחיקות שבוצעו מאז יצירתו.

## גיבוי ושחזור

הכרכים `database`, `audio`, `keys` הם מתמשכים. אין להריץ `docker compose down -v` על מערכת אמיתית.

- לפני שדרוג ובכל יום: הריצו `bash scripts/backup.sh /secure/backup/path`.
- שמרו את הגיבוי מוצפן מחוץ לשרת, הגבילו גישה למפעיל, והגדירו מחיקה אוטומטית לאחר 30 יום.
- הסקריפט עוצר לזמן קצר את View ואת API, מגבה dump של MySQL, קבצי שמע ומפתחות הצפנת עוגיות, ומחזיר את השירותים.
- שחזור: על סביבה מבודדת עם אותה גרסת קוד, הפעילו DB בלבד, ייבאו `database.sql` ל־MySQL,
  חלצו `audio.tar` לכרך השמע ו־`keys.tar` לכרך המפתחות, ואז הפעילו API ו־View.
- ודאו שחזור בפועל: כניסה, רשימת ניסיונות, השמעת הקלטה והפרדה בין שני חשבונות.
- גיבוי מפתחות מאפשר לקרוא עוגיות קיימות; יש להגן עליו כמו על סיסמה. הסשנים פגים לאחר שמונה שעות גם לאחר שחזור.

## מדדים וקבלת הפיילוט

ה־API רושם מזהה ניסיון, זמן עיבוד וסוג כשל בלבד; אין להוסיף הקלטות, תמלולים, סיסמאות או מפתחות ללוגים.
בדקו מדי יום באמצעות `docker compose logs api`: כשלים, תור ממתין ומשך ניתוח.
בדקו עלות אמיתית ב־OpenAI והגדירו תקציב והתראות בחשבון הספק.

איסוף ראשוני עם 5–10 תלמידים:

- האם תלמיד מצליח לסיים תרגול ללא עזרה?
- כמה ניסיונות הגיעו ל־Completed וכמה נכשלו? הפרידו שקט מכשל טכני.
- מה זמן ההמתנה למשוב ומה העלות הממוצעת לניסיון?
- האם מורה מאשר שהמשוב מתייחס לתשובה ושימושי לשיפור?
- האם ההרשאות, המחיקה והגיבוי עובדים בסביבת הפריסה?

בדיקות אוטומטיות עם תשובות AI מבוקרות אינן מוכיחות איכות פדגוגית. נדרשת בדיקה עם הקלטות אמיתיות ומודל פעיל.
